Devlog 003: Creating the devlog workflow

In this chapter, we set up the rule for the rest of the project: as the site is built, each meaningful lesson or change should become a new devlog chapter that another person could follow later.

Step 1: Decide what the devlog is for

The devlog is not just a change list. It should explain the project like a guided build. Each chapter should show the goal, the files changed, the code or commands used, and how to check that the step worked.

Step 2: Use a repeatable chapter template

Each new chapter should follow this shape:

  </>  HTML
<section id="devlog-005">
    <h2>Devlog 004: Chapter title</h2>

    <p>Short summary of what this chapter builds or explains.</p>

    <h3 id="example-step-id">Step 1: First action</h3>
    <p>Explain why this step matters.</p>

    <pre><code>Commands or code go here</code></pre>

    <h3 id="example-verify-step">Step 2: Verify the result</h3>
    <p>Explain what the reader should see when it works.</p>
</section>

Step 3: Make Codex part of the workflow

When Codex explains a build step, the explanation should also be turned into a devlog chapter. The chapter should be added to devlog.html, and the Chapters list on the right should be updated with links to the new section and its steps.

Step 4: Check the chapter before committing

Before pushing a chapter to GitHub, check:

  • The chapter has a unique section id like devlog-004.
  • Every linked heading has a matching id.
  • Commands are inside pre and code tags.
  • The chapter includes a way to verify the work.
  • The table of contents links to the chapter.

Step 5: Publish the devlog update

After the chapter looks right, save the project history and push it:

 </>  Powershell
git status
git add .
git commit -m "Add devlog workflow"
git push

Step 6: Save the workflow as a reference file

We also keep the workflow in DEVLOG_WORKFLOW.md so the project has a plain text reminder outside the webpage. This is useful because Codex can read it later and follow the same chapter rules. 

 </>  Markdown
# Devlog workflow

This project is both the website and the tutorial for building the website.

When Codex explains or performs a meaningful build step, add a new chapter to
`devlog.html` so the site documents its own construction.

## Chapter rules

- Use the next number: `Devlog 004`, `Devlog 005`, and so on.
- Give the section a matching id: `devlog-004`, `devlog-005`.
- Explain the goal before listing commands or code.
- Break the chapter into small steps with `h3` headings.
- Give each `h3` a unique id so the table of contents can link to it.
- Put commands and code snippets inside `pre` and `code` tags.
- Include a verification step that tells the reader what to check.
- Update the table of contents in the aside.

## Suggested chapter shape

```html
<section id="devlog-004">
    <h2>Devlog 004: Chapter title</h2>

    <p>Short summary of what this chapter builds or explains.</p>

    <h3 id="step-id">Step 1: First action</h3>
    <p>Explain why this step matters.</p>

    <pre><code>Commands or code go here</code></pre>

    <h3 id="verify-step">Step 2: Verify the result</h3>
    <p>Explain what the reader should see when it works.</p>
</section>
```

## Publishing workflow

```powershell
git status
git add .
git commit -m "Describe the devlog update"
git push
```

Devlog 004: Understanding the HTML and CSS foundation

In this chapter, we explain the HTML and CSS already used by the site, then improve the blog presentation without adding a framework yet. The goal is to understand the page before we abstract it into Astro, Markdown, MDX, or components later.

Step 1: Understand the document shell

Every HTML page starts with a small document structure. The browser reads this structure to understand the page language, character set, viewport size, title, stylesheet, and visible content. 

  </>  HTML
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Devlog | Classic Browser Games</title>
    <link rel="stylesheet" href="styles.css">
</head>
<body>
    Page content goes here.
</body>
</html>

The link tag connects the HTML file to styles.css. That keeps the content and presentation separate, which makes the project easier to change as the site grows.

Step 2: Use semantic HTML

Semantic HTML means choosing tags that describe the role of the content. A header holds site navigation, main holds the primary page content, section groups each devlog chapter, and aside holds related supporting content like the chapter list. 

  </>  HTML
<header class="site-header">...</header>
<main class="article">...</main>
<section id="example-devlog-chapter">...</section>
<aside class="table-of-contents">...</aside>

These tags make the page easier to read in the source code and give browsers, search engines, and assistive technology a better outline of the page.

Step 3: Connect headings with anchor links

The table of contents works because each chapter and step has an id. A link that starts with # jumps to the element with the matching id. 

  </>  HTML
<h3 id="example-semantic-html">Step 2: Use semantic HTML</h3>
<a href="#semantic-html">Use semantic HTML</a>

This is why every new devlog chapter needs unique ids. If two elements share the same id, the browser does not know which one you meant.

Step 4: Style the page with CSS selectors

CSS selectors choose which HTML elements receive a set of visual rules. A class selector starts with a dot, so .article styles any element with class="article". 

  </>  css
.article {
    max-width: 760px;
}

.table-of-contents {
    position: sticky;
    top: 24px;
}

CSS lets us change spacing, color, layout, typography, and responsive behavior without rewriting the HTML content.

Step 5: Improve the reading layout

The presentation update gives the devlog a more polished article layout. We added a soft page background, clearer typography, better spacing between chapters, a sticky table of contents, and cleaner code blocks. 

  </>  css
.page-layout {
    display: grid;
    grid-template-columns: minmax(0, 1fr) 280px;
    gap: 56px;
}

pre {
    overflow-x: auto;
}

The grid creates the main article column and the right-side chapter list. The overflow rule keeps long commands readable on smaller screens by allowing horizontal scrolling inside code blocks.

Step 6: Add responsive behavior

A media query changes the layout when the screen is narrow. On desktop, the article and chapter list sit side by side. On smaller screens, the layout becomes a single column so the text has enough room. 

  </>  css
@media (max-width: 900px) {
    .page-layout {
        display: block;
    }
}

Step 7: Verify the update

Open devlog.html in the browser and check that:

  • The page feels like a readable technical article.
  • The chapter list links jump to the correct sections.
  • Code blocks are readable and do not break the layout.
  • The page still works on a narrow screen.

Step 4: Break down what the stylesheet does

The stylesheet starts with broad page rules. The universal selector makes sizing more predictable, html enables smooth anchor scrolling, and body sets the default background, text color, font, and line height.

The link and nav rules style plain anchor tags into readable links and button-like navigation. The .site-header rules keep the site title and navigation aligned with the page content.

The .page-layout rule creates the two-column article layout. The main column is flexible, and the table of contents has a fixed 280px column. On smaller screens, the media query switches back to a single column.

The article, section, h2, h3, p, ul, and li rules control readability. They create spacing between ideas so the page feels like a technical article instead of one long block of text.

The pre and code rules make command and code examples readable. The dark background separates snippets from prose, and overflow-x keeps long lines from breaking the page layout.
